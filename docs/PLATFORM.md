# 多项目平台架构与开发指南

本文件随独立base-pkg仓库发布，保留上层平台的架构约定；公共包不包含下文列举的业务项目源码。

平台按公共基础能力、RPC数据模型服务、API业务入口三个板块协作。本文作为后续业务项目的导航，当前公共能力汇总以 [base-pkg接入指南](../README.md) 为准，不以历史开发流水或优化编号作为接口契约。

## 分层职责

| 板块 | 职责 | 接入入口 |
|---|---|---|
| `common-pkg` / `base-pkg` | 提供传输、上下文、认证基础设施、数据连接、响应、消息、调度和工具 | [公共包开发汇总](../README.md) |
| API | 面向用户定义接口和响应，编排业务流程并调用RPC | [API架构与接入](API.md) |
| RPC | 提供数据模型服务，管理数据访问及对应事务边界 | [RPC架构与接入](RPC.md) |

典型请求流向：用户 → 网关 → API → 多个RPC → 各自数据资源。异步任务通过消息契约协作。业务DTO、protobuf、错误码、权限及幂等策略属于业务项目；公共包不绑定特定业务领域。

## 项目依赖与版本

公共模块路径为 `github.com/K7mQ2vR9/base-pkg`，本地代码位于 `common-pkg/`。公共模块声明Go1.22.0及toolchain go1.22.4，根 `go.work` 声明Go1.25.0，当前仅纳入common-pkg。

工作区中的 `user-api`、`auth-rpc`、`user-rpc`、`common-rpc`、`es-report-rpc` 等现有项目不等于已经迁移到新公共包。接入前检查各自go.mod、replace、生成代码和导入路径；本次汇总不迁移这些项目，也不把其现有业务实现视为新架构模板。

公共包首版版本号为 `v0.1.0`，以独立仓库中该标签的源码快照为准；后续分支修改不自动包含在此版本中。新服务需配置私有仓库访问权限，并明确依赖版本及本地工作区使用方式。独立language-pkg不作为当前base-pkg的翻译依赖，词典放在各业务项目的 `etc/language`。

## 跨层共同约定

- Request ID与Trace ID共用一个值。HTTP使用 `X-Request-ID`，RPC/MQ内部传播W3C链路，业务通过 `headInfo.GetTrace(ctx)` 读取。已有合法链路不重新生成。
- 请求ctx贯穿API、RPC、数据库和外部调用。独立后台任务初始化自己的链路；共享连接在启动时创建并由服务统一关闭。
- 自定义HTTP/RPC字段使用中划线，不为下划线旧名提供别名。UID、角色和IP不能直接采信用户透传值，认证及可信代理规则见公共包说明。
- 白名单只允许正常匿名用户，不跳过结构校验、已提供Token的认证或调用方认证。业务鉴权与资源权限继续由服务实现。
- API统一响应，RPC使用标准状态及平台业务错误详情；内部诊断不直接作为公开文案。
- 数据库事务、消息结果不确定、批次部分成功、消费重投和补偿均由业务按稳定标识设计，公共包不提供跨系统恰好一次执行保证。

## 新业务项目的设计顺序

1. 划定API业务操作、RPC数据模型边界和资源所有权，先确定DTO/protobuf及错误协议。
2. 选择公共组件和明确的依赖版本，配置服务级连接池、调用预算和关闭流程。
3. 明确匿名入口、调用方身份、Token校验、用户权限及可信代理来源。
4. 贯通ctx、统一Trace、语言及业务标识，再接入数据库、搜索或消息操作。
5. 对写入和异步处理定义幂等、事务、重试、归档及人工恢复责任。
6. 根据实际环境安排所需验证，并如实说明未覆盖范围，不把示例或历史通过记录当作当前联调结论。

## 文档维护
