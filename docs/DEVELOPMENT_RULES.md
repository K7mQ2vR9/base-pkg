# 平台开发规则

## 开发前讨论方案

- `common-pkg`、RPC 和 API 的开发，先与用户讨论方案，明确改动范围、接口或兼容性影响及验证方式。用户确认方案后再开始修改业务代码。

## 代码注释

- 后续开发新增或修改的配置字段、对外接口和关键处理逻辑须补充中文注释，说明用途、默认值、单位及适用条件。
- 修改行为时同步更新相关注释，使注释与实际实现保持一致。

## 自定义传输字段命名

- 自定义 HTTP 业务头与 RPC metadata 使用中划线分词，常量以小写定义；HTTP 名称大小写不敏感，RPC 名称使用小写。不为下划线旧名增加兼容别名。
- 原终端的标准 HTTP `User-Agent` 在 RPC 中通过 `client-user-agent` 传递，避免占用 gRPC 自身保留的 `user-agent`。
- 本规则只调整传输头命名，不要求同步修改业务 JSON/JWT 字段标签。

## 统一请求 ID

- Request ID 与 Trace ID 共用一个值，对外头名为 `X-Request-ID`。已有合法 ID 时复用，API、RPC 和 RabbitMQ 链路不重复生成。
- 新请求使用加密安全随机源生成 16 个随机字节，编码为非全零的 32 位小写十六进制字符串，不带时间戳、业务前缀或连字符；格式错误、重复或冲突的入站 ID 直接拒绝。
- 网关和 API 须在创建原生 Span 前完成校验和初始化；完整生成、入口及传递规则见 [统一请求 ID 规则](../headInfo/TRACE_ID.md)。消息 ID 和业务去重标识按各自语义独立维护。
- RPC 和 RabbitMQ 内部只通过 W3C `traceparent`/`tracestate` 传递链路，删除旧 ID 字段、别名函数和旧接入入口，不保留兼容分支。业务统一使用 `headInfo.GetTrace(ctx)`。

## 测试用例清理

- 本规则适用于 `common-pkg`、RPC 和 API。每次开发使用的新增测试用例、测试脚本和临时产物须在验证完成后全部清理。
- 清理前，在对应子项目的开发记录中登记实际执行的测试命令、结果和已知限制。清理后核对本次新增的测试文件和产物均已删除，并记录清理结果。
- 清理范围为本次任务新增的内容。项目原有测试和用户已有文件继续保留。
